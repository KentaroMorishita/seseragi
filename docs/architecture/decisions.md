# 見送った案と、その理由

検討したうえで採用しなかった案を、理由と見直す条件とともにまとめます。
同じ案をもう一度検討するときに、前回の判断を確かめるための文書です。
決まった規則そのものは、仕様（`docs/spec/`）にあります。

## 任意の比較関数を受け取る `sortWith`（#369）

**判断**: 標準 API に加えない。

- 型の標準の順序は `Ord` が持ちます。表示の順や一時的な優先度は、`sortBy` で順位を表す値に写せば並べられます。
- 例: `arrays.sortBy (\value -> if value == "urgent" then 0 else 1) values` は `"urgent"` を先にし、同じ順位の要素は元の順を保ちます。
- 任意の比較関数は、2つの値の組でしか決まらない順序も表せるので、`sortBy` と同じではありません。
  しかし、それが必要な具体的な利用例がありません。
  比較関数の一貫性が崩れたときの扱い、呼び出しの回数と順、Array と List の違いを、新たに標準の約束へ加える根拠が足りません。
- 局所的な `Ord` instance や、JavaScript の比較関数が返す数値をソースへ出す経路も加えません。

**見直す条件**: `sortBy` では書けない、具体的な利用例が見つかったとき。仕様 10 章の `sortBy` の規則と一緒に変えます。

## 複数の Signal を同時に読む標準 helper（#610）

**判断**: `sample` や `snapshot` のような標準 helper も、Effect 全体の値を固定する仕組みも加えない。

- 同じ時点の値の組が必要なときは、`combine` や Applicative でレコードを返す Signal を作り、それを一度だけ読みます（仕様 5.14）。
- 実際のアプリのコマンドを調べ、この書き方で足りることを確かめました。
- 毎回 Signal を組み立て直すと、使い回すより遅くなります。それでも、新しい仕組みを加えるほどの差は測れていません。
- 非同期の処理をまたいで値を固定する仕組みは、排他や古い値の扱いを含む別の意味になります。

**見直す条件**: 一度の読み取りで表せない取得の条件が実際のアプリで見つかったとき、または測って大きなコストが確かめられたとき。

## ログの自動の相関 ID と span、共通の Error 型（#614）

**判断**: 自動で伝わる span、全体で共有する文脈、共通の Error 型や trait は加えない。

- 同じ操作のログを結びつけるときは、アプリが選んだ ID を `LogEvent.fields` に明示して渡します（仕様 9.13）。
- 失敗の値 `E` から、利用者に見せる文言と、ログに出す安全な項目を、それぞれ別の純粋な関数で作ります。
  `E` や外部のエラー、スタック、入力の値を、そのままログに出しません。
- 実行できる例: `examples/spec/fixtures/projects/log-correlation`

自動の span を加えるなら、次の条件を守ります。

- 最初の処理は、明示しない限り ID を持たない
- 子の Fiber は親の文脈を変更できない形で受け継ぎ、明示的に span を始めたときだけ自分の span を持つ
- 兄弟の Fiber の更新が、互いに影響しない
- 入れ子の scope は、成功・失敗・Defect・取消のどれで終わっても、親の文脈に戻す
- 外部のコールバックへは、明示的に渡した文脈だけが届く
- 利用者のデータや外部のエラーの文字列を、既定で付けない

**見直す条件**: 明示的に ID を渡す方法では、Provider、コールバック、取消のどれかで意味が失われる例や、重複が許容できない例が見つかったとき。

## VS Code を使う E2E テストを Node で動かす（#824）

**判断**: VS Code をダウンロードして拡張機能を試すテストは、Bun ではなく Node で動かす。

- テスト用の SDK は、ダウンロードしたアーカイブを子プロセスの `tar` へパイプで渡します。
- Bun でこれを動かすと、パイプの途中でバイトが失われ、Linux の CI でアーカイブの展開に失敗しました。
- テストの手順の準備は Bun、SDK の実行は Node（`scripts/local-web-product-e2e-node.cjs`）に分けています。
- パイプでバイトが失われないことは、`scripts/probes/local-web-product-e2e-transport-probe.cjs` で確かめます。Node で失われたらテストを失敗にします。

この判断はテストの実行環境だけのものです。生成するプログラムは Node を必要としません。
