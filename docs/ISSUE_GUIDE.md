# Issue の書き方

Issue は、この作業を初めて見る人が読んで、そのまま着手できるように書きます。
人が書く場合も、Codex や Claude が書く場合も同じです。

テンプレートは `.github/ISSUE_TEMPLATE/` にあります。
`gh issue create --template <ファイル名>` でも使えます。

## 共通の構成

本文は、次の順に並べます。type ごとの違いは「type ごとの書き方」を見てください。

| 見出し | 書くこと |
| --- | --- |
| 概要 | 何が問題か、何をするかを1〜3文で書く。対応済みの部分があれば、1行と PR へのリンクで書く |
| 対象 | 作業の範囲。API 名、ファイル、関数、入力の形などを具体的に挙げる |
| 注意点 | 守る挙動、やってはいけないこと、別の Issue で扱うもの |
| 完了条件 | チェックできる条件のリスト。満たせば閉じてよい状態を書く |
| 親 | 最後の行に `親: #番号` と書く。親がなければ省く |

ラベルは、type を1つと `area:` を1つ以上付けます。
マイルストーンは、該当するものがあれば付けます。

## タイトル

`領域: 何がどうなる` か `領域: 何をする` の形にします。

- 良い例：`compiler: Unit 引数の標準関数呼び出しが TS の strict 検査で TS2554 になる`
- 良い例：`native: std/regex の findAll・split・置換に対応する`
- 避ける例：`alias の修正`（何が起きるのかわからない）

領域は `compiler`、`runtime`、`native`、`wasm`、`web`、`lsp`、`cli`、`ci`、`docs` などです。

## 書き方

- **事実を書く。** 「確認した」「直っている」のような、書き手の作業報告は書きません。
  「〜になる」「〜は対応済み（#123）」のように、状態として書きます。
- **作業ログを書かない。** CI の実行 ID、commit hash、PID、検証の経緯、
  「試したら通った」という記録は、本文にもコメントにも書きません。
- **技術的な事実は削らない。** 再現ソース、エラーの全文、API 名、守るべき条件は、
  読みやすく並べ替えても残します。Issue を書き直すときも同じです。
- **済んだことは短く。** 対応済みの範囲は、1行と PR のリンクにまとめます。経緯の表は作りません。
- **日本語は平易に。** 「canonical」「contract」「slice」「boundary」などの英語の専門用語は
  使わず、普通の言葉で書きます。型名、キーワード、コマンド、エラーコードはそのまま書きます。
- **1文に1つのこと。** 並列の項目は箇条書きか表にします。
- **わからないことは、わからないと書く。** 推測は「原因の見立て」として、事実と分けて書きます。

## type ごとの書き方

### bug（不具合）

期待どおりに動かないもの。**再現ソースと実際の出力がない bug は起票しません。**

| 見出し | 書くこと |
| --- | --- |
| 概要 | 何が起きるか。どのターゲット（TS / native / WASM / Playground / LSP）で起きるか |
| 再現 | 最小の再現ソース、実際の出力（エラーは全文）、期待する結果 |
| 対象 | 原因がありそうなファイルや関数。わかっていれば原因の見立て |
| 注意点 | 直すときに変えてはいけない挙動、関連する Issue |
| 完了条件 | 再現ソースが期待どおりに動くこと。回帰テストがあること |

### feature（機能）

新しく使えるようにするもの、TS と native の差を埋めるもの。

| 見出し | 書くこと |
| --- | --- |
| 概要 | 何ができるようになるか。今の状態と目標の差 |
| 対象 | 対象の API・構文・コマンドを、具体的にすべて挙げる。「など」で済ませない |
| 注意点 | 揃えるべき境界のケース（空の入力、エラーの種類、評価順、リソースの解放など） |
| 完了条件 | 対象がすべて動くこと。TS と比べるものは、同じ入力で同じ結果になるテストがあること |

### investigation（調査）

やり方を決める前に、事実を集めるもの。結論は決定と後続の Issue につなげます。

| 見出し | 書くこと |
| --- | --- |
| 概要 | なぜ調べるのか。何を決めたいのか |
| 調べること | 答えるべき問いを番号付きで挙げる。計測するなら、条件も書く |
| 注意点 | 調べる範囲の外にあるもの。前提にしてはいけないこと |
| 完了条件 | 結果をこの Issue のコメントに書くこと。決定と、後続の Issue を作ること |

結果のコメントは、問いと同じ番号で答えます。最後に「決定と後続 Issue」を書きます。

### perf（性能）

速度、メモリ、ビルド時間、バイナリサイズの改善。

| 見出し | 書くこと |
| --- | --- |
| 概要 | 何が遅い・大きいのか。それがなぜ困るのか |
| 計測 | 対象（プログラムや操作）、計測の条件、今の値 |
| 対象 | 改善の候補になる箇所 |
| 注意点 | 結果・評価順・エラーの時点・リソースの解放を変えないこと |
| 完了条件 | 同じ条件で、改善の前後を比べた値があること |

### security（セキュリティ）

脆弱性や、その対応状況の追跡。

**悪用できる未修正の脆弱性は、公開 Issue に書きません。**
GitHub の Security Advisory（非公開）で扱います。
公開 Issue にするのは、上流の修正待ちや、公開済みの情報への対応だけです。

| 見出し | 書くこと |
| --- | --- |
| 概要 | どの脆弱性か（CVE や公開情報へのリンク）。何が影響を受けるか |
| 対象 | 影響を受けるサービス、パッケージ、バージョン |
| 注意点 | 誰が直すのか（自分たちか、上流か）。対応を待つ間の扱い |
| 完了条件 | 修正済みのバージョンで動いていること。どうなれば閉じるか |

### docs（ドキュメント）

| 見出し | 書くこと |
| --- | --- |
| 概要 | 何がわかりにくいのか、何が足りないのか |
| 対象 | 対象のファイルと、想定する読者 |
| 注意点 | `docs/spec/` の規則を変えるかどうか。変える場合は、そのことを明記する |
| 完了条件 | 想定する読者が、何をできるようになるか |

### tracking（まとめ）

複数の Issue をまとめて、進み具合を追うもの。tracking 自体に実装の作業は書きません。

| 見出し | 書くこと |
| --- | --- |
| 目的 | このまとまりで何を達成するか |
| 子 Issue | `- [ ] #番号 タイトル` のチェックリスト。閉じた Issue にはチェックを付ける |
| 補足 | 進める順番、まとまりの外にあるもの（あれば） |

## Issue を更新するとき

- 状態が変わったら、**本文を書き換えて**今の状態にします。経過をコメントに積み上げません。
- コメントに書くのは、調査の結果、決定、再現ソースの追加など、後から読む価値のあるものだけです。
- 範囲が広がったら、新しい Issue に分けて、元の Issue からリンクします。
- 閉じるときは、完了条件がすべて満たされているかを確かめます。
  満たさずに閉じる場合は、その理由をコメントに1文で書きます。
