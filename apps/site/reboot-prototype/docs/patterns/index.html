Guide / Data and match
02 / DATA HAS SHAPE

Choose by the shape of a value.

Sometimes you're not really asking a series of unrelated Boolean questions. You're asking what shape does this data have? A Seseragi match answers that question and produces a value. It's an expression, not a collection of exit statements.

Start with two facts, read together.

FizzBuzz is familiar enough to make the interesting part stand out: the overlap between patterns and how cases are covered. Pair the remainders from division by 3 and 5 in a tuple.

01 / Excerpt: match a tuple
match (number % 3, number % 5) {
  (0, 0) -> "FizzBuzz"
  (0, _) -> "Fizz"
  (_, 0) -> "Buzz"
  _ -> `${number}`
}

(0, 0) means both remainders are zero. _ doesn't care about the value in that position. Instead of scattering two checks everywhere, we're describing a single data shape.

Every branch produces a value.

Each arm returns a String, so the entire match has that result type. It can serve as the body of a function. Not writing return isn't just shorter syntax. Seseragi doesn't separate control-only statements from value-producing expressions in the usual way.

Here's the complete program. fizzBuzz chooses a string; the Effect returned by main prints it. Pure computation and execution have separate jobs.

fizzbuzz/main.ssrg / complete program
Run in Playground ↗
fn fizzBuzz number: Int -> String =
  // A tuple lets one match classify both divisibility rules.
  match (number % 3, number % 5) {
    (0, 0) -> "FizzBuzz"
    (0, _) -> "Fizz"
    (_, 0) -> "Buzz"
    _ -> `${number}`
  }

pub effect fn main = for number <- 1 ..= 30 {
  println $ fizzBuzz number
}

The compiler checks that nothing falls through.

An incomplete match is a compile error. An arm that can never be reached is also rejected. You cannot silently leave an alternative unexplained.

THINK ABOUT THE TYPE
IdleLoadingLoaded value

Imagine a type with three alternatives: Idle, Loading and Loaded. Those are the cases a match must account for. If a new alternative appears later, the compiler can show where handling must change. This is a conceptual diagram, not executable source.

A guard doesn't make an arm exhaustive.

when adds a Bool condition after a pattern matches. The guard might be false, so guarded arms don't contribute to exhaustiveness. Make sure the remaining values are handled elsewhere.

This doesn't mean if is somehow wrong. If the problem is a plain Boolean condition, if may be just right. Match shines when the alternatives are encoded in data such as ADTs and tuples.
