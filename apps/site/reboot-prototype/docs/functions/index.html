Guide / Functions and notation
01 / FUNCTIONS AS VALUES

You don't have to apply every argument at once.

One idea makes Seseragi functions much easier to reason about: a function is a value. Partial application isn't simply a shorthand for omitting parameters. It's how small pieces of behavior can become ingredients for other functions.

Suppose you want to reuse a search rule.

Think about filtering a list of commands. You want to ignore stray whitespace and capitalization when comparing names. Give that job its own small function first.

01 / Excerpt: normalize a name
import * as text from "std/text"

fn key name: String -> String = text.toLower (text.trim name)

key does exactly one thing. It doesn't know about searching or rendering. It trims the edges and makes the text lowercase.

Next, a function that checks whether a name starts with a query. It needs two strings.

02 / Excerpt: build a predicate
fn matches query: String -> name: String -> Bool =
  text.startsWith (key query) (key name)

Read String → String → Bool carefully. It isn't one box that must receive two strings together. It's a function that takes a string and yields another function waiting for a string.

Keep the function that's left over.

Once the query is fixed to "b", we can apply only that first argument.

03 / Excerpt: reuse the predicate
let builds = matches "b"
let choices = arrays.filter builds commands
let shortcuts = arrays.filter builds ["bundle", "run"]

builds is a String → Bool function. That's exactly what arrays.filter needs. The list can change without copying the matching logic. We're passing a function to another function.

Now put the whole program together.

Those snippets shared surrounding definitions, so here's the complete program. main returns an Effect that prints the results; key and matches just calculate values.

chapter-function-values.ssrg / complete program
Run in Playground ↗
import * as text from "std/text"
import * as arrays from "std/array"

fn key name: String -> String = text.toLower (text.trim name)
fn matches query: String -> name: String -> Bool =
  text.startsWith (key query) (key name)

let commands = [" Build ", "bundle", "CHECK", "run"]
let builds = matches "b"
let choices = arrays.filter builds commands
let shortcuts = arrays.filter builds ["bundle", "run"]

pub effect fn main = do {
  println (show choices)
  println (show shortcuts)
}

choices includes " Build " and "bundle". What happens if you use "c" as the query instead? The rest of the code can stay the same.

Why is this worth designing around?

Normalizing a name, deciding whether it matches, and filtering a list are three separate responsibilities. Instead of hiding everything inside a giant search function, we compose those smaller pieces when needed.

This behavior follows from the language's function types: multi-parameter functions are curried. Arguments are applied from left to right, and the intermediate function is a real value you can keep.

A quick comparison with JavaScript

JavaScript can express the same shape as (query) => (name) => .... In Seseragi, nested one-argument functions are the normal type interpretation of multi-parameter declarations. The point isn't saving punctuation; it's making the intermediate function useful.
