Guide / データとmatch
02 / DATA HAS SHAPE

条件ではなく、値の形で考える。

分岐を書くとき、いつも if を重ねればいいわけじゃない。データが「どんな形か」を見て、ひとつの結果を作りたいことがある。Seseragiの match は、まさにそのための式なんだ。

まず、二つの情報を一緒に見る。

FizzBuzzを題材にしてみよう。よくある例だけど、ここでは文字列の出力より、パターンの重なりと網羅性を見るために使う。3で割った余りと5で割った余りを、タプルにまとめる。

01 / 抜粋：タプルを一度に照合する
match (number % 3, number % 5) {
  (0, 0) -> "FizzBuzz"
  (0, _) -> "Fizz"
  (_, 0) -> "Buzz"
  _ -> `${number}`
}

(0, 0) は両方の余りが0。_ は「その場所の値は問わない」というパターン。二つの条件を順に重ねる代わりに、ひとつの値の形として読める。

どの枝も、ひとつの値を作る。

この match は文字列を作って返す。各枝の → の右側も式で、型はすべて String に揃っている。だから関数本体そのものを match にできる。return がないのは単なる省略ではなく、制御のための文と値を作る式を分けない設計から来ている。

全体を動かすとこうなる。fizzBuzz が文字列を決め、main のEffectがそれを表示する。値の計算と実行は別の役割だ。

fizzbuzz/main.ssrg / 完全なプログラム
Playgroundで動かす ↗
fn fizzBuzz number: Int -> String =
  // A tuple lets one match classify both divisibility rules.
  match (number % 3, number % 5) {
    (0, 0) -> "FizzBuzz"
    (0, _) -> "Fizz"
    (_, 0) -> "Buzz"
    _ -> `${number}`
  }

pub effect fn main = for number <- 1 ..= 30 {
  println $ fizzBuzz number
}

全部の状態を考えたか、コンパイラが確認する。

ここが match の大事なところ。Seseragiでは網羅的でない match はコンパイルエラーになる。逆に、すでに一致する枝の後に置かれて絶対に選ばれない枝もエラー。処理が「それ以外はどうなる？」を曖昧にしたまま通ることを許さない。

THINK ABOUT THE TYPE
IdleLoadingLoaded value

例えば型が「Idle・Loading・Loaded」の3つの状態を持つなら、考えるべき選択肢はその3つ。後から状態が増えたとき、どこを直す必要があるかコンパイラが知らせてくれる。この図は型の考え方を示すもので、実行コードではない。

guardは便利。でも網羅性には数えない。

when を使えば、パターンに一致したあとで Bool の条件を追加できる。ただし条件がFalseになるかもしれないので、guard付きの枝は網羅性には寄与しない。必要なら最後に、残りのケースを覆う枝を用意しよう。

if とどちらが正しいという話ではない。Boolの条件なら if も自然。ADTやタプルなど、値の形に応じた処理を網羅的に書きたいとき、match が特に力を発揮する。
